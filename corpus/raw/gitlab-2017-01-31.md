## Summary
On 31 January 2017, GitLab.com suffered a 23‑hour outage and permanent data loss after an engineer accidentally deleted the production database directory while trying to repair a broken replication. The replication had been disrupted after a spam‑induced load spike caused the primary to advance WAL segments faster than the secondary could consume them. A manual rebuild procedure — undocumented and without safeguards — was attempted, during which the engineer ran a destructive command on the wrong server. All backup mechanisms had failed silently: the daily pg_dump logical backup had been broken for weeks due to a PostgreSQL version mismatch, error notification emails were rejected by DMARC, and Azure disk snapshots were not enabled. Recovery required restoring a 6‑hour‑old LVM snapshot from the staging environment, hosted on slow Azure classic storage in a different region. The copy alone took 18 hours. Approximately 5,000 projects, 5,000 comments, and 700 new user accounts were permanently lost. Git repositories and wikis (stored separately on NFS) were unaffected. The incident affected only GitLab.com; self‑managed instances were not impacted.

## Timeline
- **~17:20 UTC** – Engineer manually takes an LVM snapshot of production and loads it into staging for planned pgpool‑II testing.
- **~19:00 UTC** – Database load increases sharply, driven by spam and a background job attempting to remove a GitLab employee falsely reported for abuse. Users are unable to post comments.
- **~23:00 UTC** – Replication between primary and secondary stops. Primary has already deleted WAL segments that the secondary needed; re‑synchronisation must be done manually.
- **~23:00 UTC** – Engineer wipes the secondary's data directory and runs `pg_basebackup`. The command hangs silently (it is waiting for the primary to send replication data). Multiple attempts fail.
- **~23:00 UTC (critical)** – Believing leftover files might be the problem, the engineer prepares to wipe the directory again, but accidentally executes the removal command on the **primary** server (`db1`). Around 300 GB of data is deleted before the command is terminated.
- **~23:30 UTC** – The team realises both primary and secondary are empty and begins searching for backups.
- **~23:30‑00:00 UTC** – Discovery that pg_dump backups are missing, Azure snapshots were never enabled, and the only available copy is the 6‑hour‑old staging LVM snapshot.
- **00:00 UTC** – Data loss window closes; any database modifications after 17:20 UTC are declared unrecoverable.
- **Next 18 hours** – The staging LVM snapshot is copied to production over Azure classic storage, bottlenecked by throttled disk speeds (~60 Mbps).
- **Feb 1 ~17:00 UTC** – Production database restored (without webhooks). Webhooks are recovered separately from a second copy of the snapshot. All database sequences are incremented by 100,000 to prevent ID collisions with data created during the lost window.
- **Feb 1 ~18:00 UTC** – GitLab.com fully operational.

## Root Cause
The immediate trigger was a human error: an engineer ran `rm -rf` on the primary database directory instead of the secondary during an unautomated replication recovery procedure. However, the underlying failures were:

1. **Replication broke** because a spam‑induced load spike caused the primary to advance WAL segments faster than the secondary could consume them, deleting segments before the secondary had replicated them. The load spike was compounded by a background job attempting to remove a GitLab employee whose account had been falsely reported for abuse.
2. **The replication recovery procedure** was entirely manual, poorly documented, and had no safety checks (e.g., confirmation prompts, visual host differentiation in the terminal).
3. **Multiple backup systems had failed silently:**
   - The `pg_dump` logical backup used PostgreSQL 9.2 against a 9.6 server. The Omnibus package auto‑detected the wrong version because application servers had no database data directory, defaulting to 9.2. The script had been failing for weeks.
   - Error emails from the cronjob were rejected by the receiving mail server because they lacked DMARC signatures, so no one was alerted.
   - Azure disk snapshots were not enabled for the database servers; they had been deprioritised due to slow restore times.
   - The LVM snapshot system was designed for staging copies, not disaster recovery, and the snapshot available was 6 hours old.

**GitLab's own 5‑Whys analysis** identified two problem streams:
- *Why was GitLab.com down?* → Accidental primary deletion during replication rebuild, which was needed because replication stopped, which happened due to a load spike, which was caused by spam and an erroneous employee removal triggered by an unverified abuse report.
- *Why did recovery take so long?* → Restoring from staging on slow Azure classic storage was necessary because pg_dump backups were broken, Azure snapshots were not enabled, and the secondary was also empty. The backup failure went unnoticed because DMARC rejected alerts, and nobody owned backup testing.

## Resolution
1. Engineers decided to restore from the 6‑hour‑old LVM snapshot that had been manually copied to staging at 17:20 UTC.
2. The ~300 GB data directory was copied from the staging host to the production host over Azure classic storage, taking approximately 18 hours due to throttled network disk performance (~60 Mbps).
3. Once the copy was complete, the database was restored (without webhooks to avoid accidental triggers).
4. A separate restoration process recovered the webhooks table from a second copy of the snapshot, and the data was merged.
5. All database sequence numbers were incremented by 100,000 to prevent ID collisions with data created during the lost window.
6. By Feb 1 18:00 UTC, GitLab.com was back online and fully functional.

## Prevention
GitLab committed to the following improvements:
- Automated testing of database backup restoration on a regular schedule.
- Implementation of point‑in‑time recovery (PITR) with continuous WAL archiving (evaluated tools like WAL‑E and pgBarman).
- Enabling Azure disk snapshots for production database servers.
- Increasing LVM snapshot frequency to hourly instead of daily.
- Fixing the pg_dump backup procedure to use the correct PostgreSQL version regardless of the host.
- Reliable backup failure alerting via channels that are not dependent on email DMARC.
- Documenting and automating replication rebuild procedures with mandatory safety checks (e.g., forced host verification before destructive commands).
- Improving the abuse‑reporting system to prevent accidental scheduling of user removal.
- Assigning explicit ownership for data durability and disaster recovery procedures.
- Making it visually obvious which server an engineer is connected to (e.g., coloured prompts).
