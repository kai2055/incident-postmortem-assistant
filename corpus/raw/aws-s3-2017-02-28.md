## Summary

On February 28, 2017, Amazon S3 in the Northern Virginia (US-EAST-1) region experienced a service disruption lasting roughly 4 hours and 17 minutes, from the trigger at 9:37 AM PST to full recovery at 1:54 PM PST. While the S3 team was debugging an issue that was slowing the S3 billing system, an authorized team member used an established playbook to run a command intended to remove a small number of servers from one of the S3 subsystems used by the billing process. One of the inputs to the command was entered incorrectly, and a larger set of servers was removed than intended. The inadvertently removed servers supported two other S3 subsystems: the index subsystem, which manages the metadata and location information of every S3 object in the region and is required for all GET, LIST, PUT, and DELETE requests; and the placement subsystem, which allocates storage for new objects during PUT requests and depends on the index subsystem. Removing that much capacity forced both subsystems into a full restart, during which S3 could not service requests. Other US-EAST-1 services that rely on S3 — the S3 console, EC2 new instance launches, EBS volumes that needed data from S3 snapshots, and AWS Lambda — were impacted while the S3 APIs were unavailable. The restart took longer than expected because these subsystems had not been fully restarted in the larger regions for many years and S3 had grown enormously in that time. The index subsystem began serving GET, LIST, and DELETE requests by 12:26 PM and was fully recovered by 1:18 PM; the placement subsystem (and the PUT API) recovered at 1:54 PM, after which S3 operated normally.

## Root Cause

The disruption was caused by an operator command-input error during routine maintenance, which then exposed how long these subsystems take to restart at scale.

1. **Incorrect command input.** While debugging the slow S3 billing system, an authorized team member used an established playbook to run a command meant to remove a small number of servers from a billing-related S3 subsystem. One input was entered incorrectly, so the command removed a much larger set of servers than intended.

2. **Unintended subsystem impact.** The servers removed supported two other subsystems. The index subsystem manages the metadata and location of all S3 objects in the region and is required for every GET, LIST, PUT, and DELETE. The placement subsystem allocates storage for new objects during PUTs and itself depends on the index subsystem. Losing that capacity forced both into a full restart.

3. **Restart slower than expected.** S3 is explicitly designed to tolerate removal or failure of significant capacity, and capacity removal is a core operational process — but the index and placement subsystems had not been completely restarted in the larger regions for many years. Given S3's massive growth, restarting them and running the safety checks to validate metadata integrity took longer than expected, extending the outage.

## Resolution

1. **Index subsystem restart** — The index subsystem was the first that had to be restarted. By 12:26 PM PST it had activated enough capacity to begin serving GET, LIST, and DELETE requests.
2. **Index subsystem fully recovered** — By 1:18 PM PST the index subsystem was fully recovered and the GET, LIST, and DELETE APIs were functioning normally.
3. **Placement subsystem restart** — The placement subsystem could only recover once the index subsystem was functional; it began recovering at that point and finished at 1:54 PM PST, restoring the PUT API.
4. **Full resolution and backlog clearing** — At 1:54 PM PST S3 was operating normally. Other AWS services impacted by the event then recovered, with some requiring additional time to work through backlogs accumulated during the disruption.

## Prevention

AWS made changes across the operational tooling, recovery design, and status communication.

On the tool that triggered the event, AWS found it had allowed too much capacity to be removed too quickly. They modified it to remove capacity more slowly and added a safeguard preventing capacity from being removed if doing so would take any subsystem below its minimum required capacity level — which would have prevented this incorrect input from causing the event. They also began auditing their other operational tools to ensure similar safety checks exist.

On recovery time, AWS relies on breaking services into small partitions called cells so recovery processes can be thoroughly tested even for large subsystems. Because the index subsystem's recovery still took longer than expected, AWS reprioritized already-planned further partitioning of the index subsystem to begin immediately, to reduce blast radius and improve recovery time.

On communication, because the Service Health Dashboard's admin console itself depended on S3, AWS had been unable to update per-service status until 11:37 AM and had to rely on Twitter and a banner. AWS changed the SHD admin console to run across multiple AWS regions so it remains usable during a regional event.
